# 第 4 章 分词器

在第 3 章我们实现了完整的最小 GPT，但模型的输入不是字符串，而是整数序列。把文本切分成模型可见的基本单元（token）并映射为整数 ID 的组件，就是**分词器（tokenizer）**。分词器处于"文本世界"与"模型世界"的边界，它的选择决定了词表大小、序列长度、处理未知词的能力，甚至影响模型的多语言能力与算术推理能力。本章从为什么需要子词出发，完整推导 BPE、WordPiece、Unigram 三大算法，介绍 SentencePiece 与字节级 BPE 两种工程方案，并动手从零写一个不依赖任何库的 BPE。

## 4.1 为什么需要子词分词

### 4.1.1 词级与字符级的两难

假设我们按"词"分词，每个词一个 ID：

- **词表爆炸**：英语的词汇量轻松超过 50 万（含变形、专有名词），中文按词切分也需要数十万词条。巨大的词表使输入嵌入矩阵 $V \times d$ 与输出投影成为参数与显存大户（$V=500000$、$d=4096$ 时仅词表就 $2 \times 10^9$ 参数），且 softmax 计算量同步膨胀。
- **OOV（out-of-vocabulary）问题**：新词、人名、错拼、代码标识符在词表中不存在，只能映射为 `<UNK>`，信息全部丢失。
- **形态学关系断裂**："play / played / playing" 成为三个互不相关的 ID，模型难以共享知识。

退而求其次按"字符"分词（中文按字、英文按字母）：

- 词表极小（英文 26 个字母 + 标点），永无 OOV。
- 但序列变得极长：一个英文单词平均 4~5 个字符，同样文本的 token 数是词级的 4~5 倍，而注意力复杂度是 $O(n^2)$——上下文有效长度大幅缩水；且单个字符携带的语义太少，模型需要在底层花大量容量做字符组合。

### 4.1.2 子词：两者的折中

**子词（subword）** 的思想是：高频词保留为完整 token，低频词拆成更小的片段。例如 "tokenization" 若不在词表中，可拆为 "token" + "ization"。这样：

- 词表大小适中（几万到十几万）；
- 理论上不产生 OOV——最坏情况可以一路拆到字符甚至字节；
- 形态相近的词共享子词，参数效率高；
- 高频词不被拆碎，序列长度接近词级。

所有主流 LLM（GPT、Llama、Qwen、DeepSeek）用的都是子词方案，主要是 BPE 及其变体。

### 4.1.3 怎么衡量一个分词器的好坏

工程上常用的指标：

- **压缩率 / fertility（生育率）**：每 token 平均对应的字符数（或每词对应的 token 数）。越高越好——同样文本占用上下文更少、推理更便宜。比较时必须注明语言与领域（英文 fertility 接近 1 token/词，中文按字方案也是 1，但跨语言模型在低资源语言上可能到 2~4）。
- **覆盖率 / OOV 率**：测试文本中需要回退到字节/UNK 的比例。
- **无损往返**：`decode(encode(x)) == x` 必须严格成立，否则生成内容会"悄悄损坏"（空格丢失、全半角变化是常见 bug）。
- **词表利用率**：词表中大量 token 在真实语料中几乎不出现（训练不充分、浪费参数），理想情况下载荷分布应与语料匹配。

后面几节的算法选择，最终都要落到这几个指标上做取舍。

### 4.1.4 中文的特殊性

中文没有空格分隔，天然以"字"为单位（约 7000 常用字），这带来几个特点：

1. **字符级在中文几乎就是词级**，中文按字分词并不丢人——早期模型词表里的中文条目多是单字与常用双字词。
2. **BPE 在中文上的单位选择**：若以字为初始词表，BPE 能学出高频双字、三字词（如 "机器""学习"）；GPT-2 的字节级 BPE 在中文上曾因字节切分导致 1 个汉字占 2~3 个 token，效率低下；GPT-4（cl100k）与 Qwen 系列大幅扩充中文词表，1 个汉字通常 1 个 token。
3. **中英混排、全半角、繁简体**都会影响切分统计，是中文分词器工程的常见坑。

顺带一提，传统 NLP 的"中文分词"（jieba、THULAC 等基于词典或统计的切词）解决的是**给定词表如何切**，而子词分词器解决的是**从语料学出词表**——两者层次不同。现代 LLM 训练自己的分词器时通常不再依赖 jieba：直接把汉字（或字节）作为初始符号，让 BPE 自己发现高频双字词、三字词。也有工作（如早期 ERNIE 类模型）先用词典分词再训练，但这引入了对分词工具质量的依赖，已非主流。

分词粒度还直接影响成本与体验：tokenizer 压缩率（每 token 对应的字符数）越高，同样文本占用的上下文越少、推理越便宜。

## 4.2 Byte Pair Encoding（BPE）

BPE 原本是 1994 年的一种数据压缩算法，Sennrich 等人 2016 年将其引入 NLP 作为子词分词方法（arXiv:1508.07909）。**核心思想：从字符（或字节）出发，反复合并语料中出现频次最高的相邻符号对，直到词表达到目标大小。**

### 4.2.1 训练算法

**输入**：语料（已按词切分并统计词频）、目标合并次数/词表大小。
**输出**：合并规则表（有序！顺序决定优先级）与词表。

伪代码：

```text
BPE-Train(语料词频表 corpus, 目标合并数 M):
    vocab ← 语料中所有字符                # 初始词表 = 字符集
    merges ← 空列表
    把每个词表示为字符序列, 并记录词尾标记 </w>
    for m = 1 .. M:
        统计所有相邻符号对 (a, b) 的加权频次:
            count[(a,b)] ← Σ_词 w 中出现 (a,b) 的次数 × 词频(词 w)
        (a*, b*) ← argmax count
        若最大频次为 1, 跳出循环           # 没有值得合并的对了
        merges.append((a*, b*))
        vocab.append(a* + b*)             # 新符号 = 拼接
        对每个词的字符序列, 把所有 (a*, b*) 替换为 a*b*
    return vocab, merges
```

注意两点：(1) 频次是**按词频加权**的——"t h"在 "the"（出现 100 次）中贡献 100；(2) merges 是有序列表，编码时必须按训练时的优先级依次应用。

> 📌 注：为什么要给词尾加 `</w>` 标记？因为预分词已经切好了词边界，BPE 只在词内合并；若不加标记，"low" 里的 "ow" 与 "ower" 里的 "ow" 会被合并成同一个 token，编码时无法区分"ow 出现在词尾"与"ow 出现在词中"——前者可以独立成词，后者后面还有字母。`</w>` 把位置信息编进符号本身，等价于让"low</w>"与"low（前缀）"成为两个不同的 token。这与 WordPiece 用 `##` 标词中片段是同一目的的两种写法。另外，本章伪代码的统计口径是"对每对只计一次、按词频加权"（与 HuggingFace 训练器一致）；有的教程按"出现次数"逐位置累计，两种口径在同一份数据上结果相同，因为同一对在一个词内的相对次序不受口径影响。更多细节见 HuggingFace [tokenizers 文档](https://huggingface.co/docs/tokenizers/index) 与 Sennrich 原论文附录。

关于贪心合并还有两个值得思考的性质。其一，**顺序敏感**：合并规则一旦生成便固定次序，先合并出的符号会参与后续统计，因此即使两条频次并列的对，先后选择不同也会产生不同的词表——BPE 是确定性贪心，不是全局最优。其二，**频次偏爱常见词**：BPE 会优先把高频词（"the""的"）合成单 token，而形态规则但频次略低的模式（如后缀 "tion"）可能需要更多合并轮次才浮现。Unigram LM（4.3.2 节）正是对这类贪心偏差的修正。此外，若语料含错拼或噪声，BPE 会忠实地把高频错误拼法学成 token——分词器继承语料的偏见，这也是数据清洗（第 5 章）要在分词之前完成的原因之一。

### 4.2.2 编码算法

```text
BPE-Encode(词 w, merges):
    symbols ← w 的字符序列
    while len(symbols) > 1:
        在 symbols 中找出所有相邻对, 选出在 merges 中排名最靠前(优先级最高)的对 (a,b)
        若没有任何对出现在 merges 中, 跳出
        把 symbols 中所有 (a,b) 合并为 ab
    return symbols                         # 每个符号查词表得 token ID
```

### 4.2.4 手写 Python 实现（无第三方依赖）

下面是约 60 行的完整 BPE：训练 + 编码 + 解码。

```python
import re
from collections import Counter

class SimpleBPE:
    """最简 BPE 分词器：以字符为初始符号，词尾加 '</w>'"""

    def __init__(self, num_merges=50):
        self.num_merges = num_merges
        self.merges = {}          # (a, b) -> 优先级(越小越先合并)
        self.vocab = {}           # 符号 -> id

    def get_pairs(self, word_freqs):
        """统计所有相邻符号对的加权频次"""
        pairs = Counter()
        for word, freq in word_freqs.items():
            syms = word.split(" ")
            for a, b in zip(syms, syms[1:]):
                pairs[(a, b)] += freq          # 按词频加权
        return pairs

    def train(self, text):
        # 1) 简易预分词 + 词频统计（英文按非字母切词）
        words = re.findall(r"\w+|[^\w\s]", text.lower())
        word_freqs = Counter(" ".join(w) + " </w>" for w in words)
        # 2) 迭代合并
        for i in range(self.num_merges):
            pairs = self.get_pairs(word_freqs)
            if not pairs or max(pairs.values()) < 2:
                break                            # 无高频对可合并
            best = max(pairs, key=pairs.get)     # 频次最高的对
            self.merges[best] = i
            merged = best[0] + best[1]
            # 3) 在所有词里应用该合并
            new_freqs = {}
            for word, freq in word_freqs.items():
                syms = word.split(" ")
                out, j = [], 0
                while j < len(syms):
                    if (j < len(syms) - 1
                            and (syms[j], syms[j + 1]) == best):
                        out.append(merged); j += 2   # 合并相邻对
                    else:
                        out.append(syms[j]); j += 1
                new_freqs[" ".join(out)] = new_freqs.get(" ".join(out), 0) + freq
            word_freqs = new_freqs
        # 4) 收集最终词表
        for word in word_freqs:
            for sym in word.split(" "):
                if sym not in self.vocab:
                    self.vocab[sym] = len(self.vocab)
        return self

    def encode_word(self, word):
        """按合并优先级从高到低反复应用 merges"""
        syms = list(word.lower()) + ["</w>"]
        while len(syms) > 1:
            # 找当前序列中优先级最高(merge 值最小)的相邻对
            candidates = [(self.merges[(a, b)], i)
                          for i, (a, b) in enumerate(zip(syms, syms[1:]))
                          if (a, b) in self.merges]
            if not candidates:
                break
            _, i = min(candidates)
            syms = syms[:i] + [syms[i] + syms[i + 1]] + syms[i + 2:]
        return syms

    def encode(self, text):
        ids = []
        for w in re.findall(r"\w+|[^\w\s]", text.lower()):
            for sym in self.encode_word(w):
                ids.append(self.vocab.get(sym, self.vocab["</w>"]))  # 未知回退
        return ids

if __name__ == "__main__":
    corpus = ("low low low low low lower lower newest newest newest "
              "newest newest newest widest widest widest")
    bpe = SimpleBPE(num_merges=10).train(corpus)
    print("合并规则:", list(bpe.merges)[:6])
    print("编码 'lowest':", bpe.encode_word("lowest"))   # 期望得到 ['low', 'est</w>']
```

这段实现刻意保持简单（忽略正则预分词的细节、并行优化），但完整覆盖了 BPE 的两个本质：**训练时的贪心高频合并**与**编码时的优先级重放**。工业级实现（HF tokenizers、tiktoken）用优先队列与增量统计把复杂度从 $O(M \cdot |\text{语料}|)$ 降到近似线性，并支持并行编码。

## 4.3 WordPiece 与 Unigram LM

### 4.3.1 WordPiece

WordPiece（用于 BERT、DistilBERT 等）与 BPE 训练流程几乎相同，唯一区别在**合并准则**：BPE 选频次最高的对，WordPiece 选使语言模型似然提升最大的对：

$$\text{score}(a, b) = \frac{f(ab)}{f(a) \cdot f(b)}$$

即合并后符号频次除以两个部分频次之积——不只看绝对频次，还看"相对于随机共现的超出程度"。频次低但结合紧密的对（如不常见但形态固定的词根词缀）也可能被优先合并。

用一个数字感受差别：设 $f(\text{es}) = 9$、$f(\text{e}) = f(\text{s}) = 9$，则 BPE 直接看频次 9；WordPiece 得分为 $9/(9 \times 9) = 1/9$；而另一对 $f(\text{xy}) = 5$、$f(\text{x}) = f(\text{y}) = 5$ 得分 $5/25 = 1/5$，反而更高——尽管频次更低，但"x 与 y 几乎总是连在一起"这一规律更强。WordPiece 因此更倾向于合并"内聚"的片段，而不是碰巧高频的组合。

**编码**：WordPiece 采用**最长匹配（greedy longest-match-first）**——从词首出发，找词表中存在的最长前缀作为一个 token，剩余部分继续。词内延续片段用 `##` 前缀标记，例如：

```text
"unhappiness" → ["un", "##happi", "##ness"]
```

`##` 使"词首片段"与"词中片段"是不同 token，保留了一点位置信息（这是它与 BPE 用 `</w>` 词尾标记的不同取向：BPE 通常标词尾，WordPiece 标词中）。

### 4.3.2 Unigram LM

Unigram（SentencePiece 的可选算法，arXiv:1804.10959）走的是**概率生成 + 删减**路线，而非逐步合并：

1. **初始化**：用候选生成（所有子串、BPE 结果等）构造一个超大的初始"子词池"；
2. **建模**：假设每个 token 独立采样，句子 $x$ 的概率是其切分 $S$ 下各子词概率之积：

$$P(x) = \max_{S \in \mathcal{S}(x)} \prod_{t \in S} p(t)$$

3. **EM 估计**：E 步用动态规划求出每个句子的最优切分（Viterbi），统计各子词的使用频次；M 步重估 $p(t) = \dfrac{c(t)}{\sum_{t'} c(t')}$；
4. **删减**：按每删除一个子词对总似然的损失排序（损失最小者先删），删掉大部分子词，直至词表达到目标大小；保留单字符以保证可覆盖。

**Viterbi 分词**：编码一个新词时，在字符位置上做动态规划——设 $\text{best}(i)$ 为前 $i$ 个字符的最优切分对数概率，则

$$\text{best}(i) = \max_{j < i,\ x[j{:}i] \in V}\left[\text{best}(j) + \log p(x[j{:}i])\right]$$

回溯即得概率最大的切分。相比 BPE 的贪心重放，Unigram 的编码是全局最优（在该概率模型下），且同一模型天然支持多种采样式分词（subword regularization，训练时随机采次优切分以增强鲁棒性）。

三者对比：

| | BPE | WordPiece | Unigram |
|---|---|---|---|
| 训练方向 | 自底向上合并 | 自底向上合并 | 自顶向下删减 |
| 合并/保留准则 | 对频次最高 | 似然增益最大 | 似然损失最小 |
| 编码方式 | 按优先级重放合并 | 最长前缀贪心匹配 | Viterbi 最大概率切分 |
| 多种切分 | 否 | 否 | 是（可采样） |
| 代表模型 | GPT、Llama | BERT | T5、ALBERT |

## 4.4 SentencePiece 与字节级 BPE

### 4.4.1 SentencePiece

SentencePiece（arXiv:1808.06226）是一个**分词器框架**而非新算法，内部可跑 BPE 或 Unigram。两大设计决策：

1. **语言无关**：不依赖空格预分词，把空格当作普通字符（转义为 `▁`，U+2581）直接进入 BPE/Unigram 训练，因此对中文、日文等无空格语言无需额外分词工具。

   ```text
   "hello world" → ["▁hello", "▁world"]
   ```
2. **内置字节回退（byte fallback）**：开启后词表包含全部 256 个字节 token，任何不能被子词覆盖的字符（生僻 emoji、罕见文字）都退化为 UTF-8 字节序列——彻底消灭 OOV。Llama、Qwen 都采用此方案。

用 SentencePiece 的命令行训练一个中文 Unigram 分词器只需：

```bash
spm_train --input=corpus.zH.txt --model_prefix=zh_sp \
  --vocab_size=32000 --model_type=unigram \
  --byte_fallback --character_coverage=0.9995
```

`--character_coverage` 指定直接收录的字符覆盖率（0.9995 表示覆盖 99.95% 的字符，长尾交给字节回退），`--model_type=bpe` 则切换为 BPE 算法。Python 侧 `sentencepiece.SentencePieceProcessor` 提供 `encode/decode` 与 `piece_size` 等接口。

### 4.4.2 字节级 BPE（GPT-2 / GPT-4 方案）

GPT-2 的做法更彻底：**不以字符而以字节为初始符号**。任何字符串先编码为 UTF-8 字节序列（256 种可能），BPE 在字节层面合并。好处：

- **理论上零 OOV**：256 个字节覆盖一切 UTF-8 文本，无需 `<UNK>`，无需回退逻辑——任意输入都能被编码，也能无损解码回原字符串；
- 词表下界只有 256，对任何语言、代码、乱码都有兜底。

> 📌 注：为什么"256 个字节"就够？UTF-8 是一种**前缀无关编码**：每个 Unicode 字符被编码为 1~4 个字节，且多字节序列的首字节（`E0`–`EF` 等）与后续字节（`80`–`BF`）取值区间互不重叠，因此任意字节流都能被唯一地重新切回字符序列——这正是"无损往返"得以成立的编码学基础。一个汉字通常占 3 个字节（U+4E00–U+9FFF 区间），一个 emoji 占 4 个字节。详见维基百科 [UTF-8](https://en.wikipedia.org/wiki/UTF-8)。可用一行代码体会：`list("温".encode("utf-8"))` 得到 `[230,184,169]`。

代价：未经优化的字节级 BPE 在非拉丁文字上很浪费（一个汉字 3 字节 → 可能 2~3 个 token）。因此 GPT-4（cl100k_base）、o200k_base 以及 Qwen、DeepSeek 的词表都大幅增加了中文等多语言子词，把常用汉字压回 1 个 token。

GPT-2 同时定义了一套**预分词正则**，先把文本切成"永不跨界的片段"（如 `\p{L}+`、`\s+(?<!\S)`、数字串等），BPE 在片段内进行——防止合并规则把空格、标点与单词胡乱拼在一起。可以对照理解 SentencePiece 与字节级 BPE 对"空格"的两种处理：SentencePiece 把空格显式转义成 `▁` 并当作子词的一部分（"▁hello"），GPT-2 则把"空格 + 词"一起做成 token（"Ġhello"，Ġ 是字节 0x20 的可视字符），殊途同归——都是为了让模型显式看到词边界。

实际使用中，OpenAI 的 tiktoken 库（github.com/openai/tiktoken）提供了这些词表的高性能实现：

```python
import tiktoken
enc = tiktoken.get_encoding("o200k_base")      # GPT-4o
ids = enc.encode("大语言模型 Hello!")
print(ids, enc.decode(ids))                     # 无损往返
```

### 4.4.3 词表演进：从 GPT-2 到 GPT-4o

把主流模型的词表放在一起看，能读出分词器设计的时代脉络：

| 模型 | 词表 | 方案 | 特点 |
|---|---|---|---|
| GPT-2 (2019) | 50,257 | 字节级 BPE | 零 OOV，但中文 1 字 ≈ 2~3 token |
| Llama-2 (2023) | 32,000 | SentencePiece BPE + 字节回退 | 以拉丁字母为基、中文偏费 |
| GPT-3.5/4 (2022-23) | ~100,000 (cl100k) | 字节级 BPE | 大幅扩充多语言与代码 |
| Llama-3 (2024) | 128,256 | tiktoken 风格 BPE | 中文压缩率显著提升 |
| GPT-4o (2024) | ~200,000 (o200k) | 字节级 BPE | 多语言进一步优化 |
| Qwen2.5 (2024) | ~151,000 | 字节级 BPE | 中英双语与代码均衡 |

规律很清晰：随训练预算与多语言需求增长，词表从 3~5 万扩到 10~20 万；方案收敛到字节级 BPE（或带字节回退的 SentencePiece BPE），Unigram 在 LLM 基座中已少见（更多留在 T5 系与学术工作）。词表每翻一倍，嵌入与输出头参数（$\approx 2Vd$）随之翻倍，因此扩词表的决策本质是用参数换上下文利用率，只有当训练语料足够多、多语言占比足够高时才划算。

## 4.5 词表大小、特殊 token 与聊天模板

### 4.5.1 分词器如何塑造模型能力

分词器不是"透明的前处理"，它直接定义了模型看到的原子世界，至少影响三种能力：

1. **算术**：如果数字被逐位切成 token（"2024" → "2","0","2","4"），模型做加法时要处理任意长度的数字序列；若切成三位一组（"1","234","567"，Llama 系的做法），模型能学到千进制结构，多位数运算明显更准。
2. **代码**：代码中的缩进、长标识符、罕见符号很多。GPT 系词表专门为代码优化（如把 4 空格缩进、常见关键字、`>::` 等符号序列并入 token），这直接提升了代码模型的有效上下文。
3. **多语言公平性**：同一模型对英文 1 token/词、对某小语种 4 token/词，意味着该语言用户付出 4 倍的上下文与费用、且有效上下文缩短 4 倍——分词器的"语言税"是 LLM 公平性问题的重要来源。

反过来，改分词器必须重训（或至少续训）嵌入层：token ID 的语义完全由训练赋予，把两个模型的词表混用是不成立的。这也是"给 Llama 扩中文词表"类工作的基本流程：改词表 → 初始化新嵌入（均值或随机）→ 继续预训练。

### 4.5.2 词表大小的权衡

| 词表增大 | 收益 | 代价 |
|---|---|---|
| | 压缩率提高（序列更短，注意力/推理更省） | 嵌入与输出投影参数 $\approx 2Vd$ 增大 |
| | 多语言、专业词覆盖更好 | softmax 计算与显存增大 |
| | 高频词完整保留，语义单元更完整 | 低频 token 训练不充分，表征质量差 |

经验区间：早期模型 3~5 万（Llama-1/2 为 32K），现代模型因多语言需求扩到 10~25 万（Llama-3 128K、GPT-4o ~200K、Qwen2 152K）。$V=128256$、$d=4096$ 时词表部分参数 $\approx 2 \times 128256 \times 4096 \approx 1.05\text{B}$——小模型（1~3B）中词表可占总参数 30% 以上，这是小模型常共享输入/输出嵌入（weight tying）的原因。

### 4.5.3 特殊 token

词表中通常预留一些**不对应任何自然文本**的控制 token：

- `<|begin_of_text|>`（BOS）：序列起始；
- `<|end_of_text|>`（EOS）：终止生成；
- `<|pad|>`（PAD）：批内补齐，注意力需配 padding mask；
- `<|unk|>`（UNK）：未知符号（字节级方案下通常不再需要）；
- 训练分隔符：GPT-2 的 `<|endoftext|>` 兼作文档边界。

### 4.5.4 聊天模板（ChatML）

对话模型要求输入结构化地拼装用户/助手轮次，这个拼装规则就是**聊天模板**。以 ChatML（被 Qwen 等广泛采用）为例：

```text
<|im_start|>user
请用一句话介绍注意力机制<|im_end|>
<|im_start|>assistant
注意力让每个位置按相关性加权汇聚全序列信息<|im_end|>
```

训练 SFT 时（第 10 章），通常只在助手回复部分计算损失，提示词部分被掩码。模板 token 必须与 tokenizer/训练完全一致——线上少拼一个 `<|im_end|>` 是"模型停不下来"这类部署事故的常见根源。HuggingFace 的 `apply_chat_template` 统一封装了各模型的模板。

## 4.6 用 HuggingFace tokenizers 训练 BPE

```python
from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

# 1) 字节级 BPE 模型，带未知 token
tokenizer = Tokenizer(models.BPE(unk_token="<|unk|>"))
tokenizer.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
tokenizer.decoder = decoders.ByteLevel()

# 2) 训练器：目标词表大小、特殊 token
trainer = trainers.BpeTrainer(
    vocab_size=8000,
    special_tokens=["<|pad|>", "<|bos|>", "<|eos|>", "<|unk|>"],
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),  # 256 个字节打底
)
tokenizer.train(["data/corpus.txt"], trainer)   # 传文件列表

# 3) 编码 / 解码
enc = tokenizer.encode("机器学习是人工智能的核心")
print(enc.tokens, enc.ids)
print(tokenizer.decode(enc.ids))

tokenizer.save("my_bpe.json")                    # 保存可复用
```

要点：`initial_alphabet` 保证 256 个字节全部入表（即字节级方案）；`pre_tokenizer` 决定片段边界；工业级训练支持多进程与流式读取，亿级语料几分钟即可完成。转换成 `transformers` 的 `PreTrainedTokenizerFast` 即可配合任何模型使用：

```python
from transformers import PreTrainedTokenizerFast
tok = PreTrainedTokenizerFast(
    tokenizer_file="my_bpe.json",
    bos_token="<|bos|>", eos_token="<|eos|>",
    pad_token="<|pad|>", unk_token="<|unk|>")
ids = tok("机器学习是人工智能的核心")["input_ids"]
print(tok.convert_ids_to_tokens(ids))
print("压缩率(字符/token):",
      len("机器学习是人工智能的核心") / max(len(ids) - 1, 1))  # 去掉 BOS
```

训练完成后值得做的体检：(1) 在留出语料上算压缩率与 OOV/字节回退率；(2) 抽查高频词是否被切成可疑的碎片（如 "▁the" 应是单 token）；(3) 验证 `decode(encode(x)) == x` 的无损往返。这些检查能在训练模型之前就发现分词器层面的设计缺陷，避免"词表错了、模型白训"的惨剧。

## 本章小结

- 词级分词有词表爆炸与 OOV 之痛，字符级则序列过长、语义过稀；**子词（以 BPE 为代表）是主流折中**，高频词完整保留、低频词拆解、最坏回退到字符/字节。
- **BPE**：训练时反复合并语料中（按词频加权）频次最高的相邻对，编码时按优先级重放合并规则；天然可处理未登录词。
- **WordPiece**：合并准则改为似然增益 $f(ab)/(f(a)f(b))$，编码为最长前缀贪心匹配，词中片段带 `##` 前缀。
- **Unigram**：自顶向下，以 unigram 语言模型似然为目标做 EM 与删减，编码用 Viterbi 求最优切分，支持多种采样切分。
- **SentencePiece**：语言无关（空格普通字符化 `▁`）、支持字节回退；**字节级 BPE**（GPT 系）以 256 字节打底，理论零 OOV、可无损往返。
- 词表大小是压缩率与参数量的权衡，现代多语言模型普遍 10 万级；特殊 token（BOS/EOS/PAD）与聊天模板（ChatML 等）是训练与部署一致性的关键细节。

### 实操：编程练习

**练习 A：字节级 BPE 合并统计器。** 不做预分词、直接以"字节"为初始符号统计相邻对频次——这是 4.4.2 节 GPT-2 方案的最小内核。注意：字符级每个汉字是 1 个符号，字节级则是 3 个。

```python
from collections import Counter

def byte_pair_counts(chunk):
    """统计一段字节序列中所有相邻字节对的频次。chunk: list[int]"""
    return Counter(zip(chunk, chunk[1:]))

def merge(chunk, pair, new_id):
    """把 chunk 中所有相邻 pair 替换为 new_id（贪心从左到右）。"""
    out, i = [], 0
    while i < len(chunk):
        if i < len(chunk) - 1 and (chunk[i], chunk[i + 1]) == pair:
            out.append(new_id); i += 2
        else:
            out.append(chunk[i]); i += 1
    return out

def train_byte_bpe(text, num_merges=8):
    """在单块文本上做字节级 BPE（教学版：无预分词、无增量优化）。"""
    ids = list(text.encode("utf-8"))                 # 初始符号 = 字节（0~255）
    print(f"初始: {len(ids)} 个字节, 前 8 个: {ids[:8]}")
    merges = {}
    for m in range(num_merges):
        counts = byte_pair_counts(ids)
        if not counts:
            break
        pair = counts.most_common(1)[0][0]           # 频次最高的相邻对
        new_id = 256 + m                             # 新 token 从 256 起编号
        merges[pair] = new_id
        ids = merge(ids, pair, new_id)
        print(f"合并 {m+1}: {pair} (0x{pair[0]:02x},0x{pair[1]:02x}) "
              f"频次 {counts[pair]} -> id {new_id}, 剩余符号 {len(ids)}")
    return ids, merges

ids, merges = train_byte_bpe("low low low lower " * 3, num_merges=8)
# 预期输出（节选）：
#   初始: 54 个字节, 前 8 个: [108, 111, 119, 32, 108, 111, 119, 32]  (即 l,o,w,空格,...)
#   合并 1: (108, 111) 即 b'l'+b'o' —— 相邻 12 次，最高频，剩余 42 个符号
#   合并 2: ('lo', 'w') 得到 b'low'，剩余 30 个
#   合并 3: (0x20, 'low') 空格与 low 相邻 11 次，并到一起……
#   每合并一次符号数递减——这就是"压缩"的量化体现
```

**练习 B：统计合并前后 token 数（压缩率）并验证可还原。** 字节级 BPE 的"无损"意味着：按 merges 的逆序（后合并的先拆开）可以把 ID 序列还原回原始字节。

```python
def decode_byte_bpe(ids, merges):
    """把合并后的 id 序列还原回字符串（验证无损往返）。"""
    rev = {v: k for k, v in merges.items()}
    stack = list(ids)
    changed = True
    while changed:                                   # 反复合并的逆操作
        changed, out = False, []
        for i in stack:
            if i in rev:                             # 新 id 拆回原来的字节对
                out.extend(rev[i]); changed = True
            else:
                out.append(i)
        stack = out
    return bytes(stack).decode("utf-8")

text = "low low low lower 低 低 低"
raw = len(text.encode("utf-8"))                       # 原始字节数
ids, merges = train_byte_bpe(text + " " * 10, num_merges=10)
print(f"压缩率 = {raw / len(ids):.2f} 字节/token")
print("无损还原:", decode_byte_bpe(ids, merges) == (text + " " * 10))
# 预期：压缩率 > 1（重复文本下可到 2~4），无损还原: True
```

**练习 C：对比三个工业分词器的压缩率。** 用 tiktoken 量化 4.4.3 节"词表演进"的实际效果（`pip install tiktoken`）。

```python
import tiktoken

zh = "大语言模型正在改变世界。The quick brown fox jumps over the lazy dog. 12345"
for name in ["gpt2", "cl100k_base", "o200k_base"]:
    enc = tiktoken.get_encoding(name)
    n = len(enc.encode(zh))
    print(f"{name:>12}: {n:3d} tokens, 压缩率 {len(zh)/n:5.2f} 字符/token")
# 典型输出（随版本略有差异）：
#        gpt2: ~60 tokens —— 中文按字节切，1 个汉字约 2~3 token，最浪费
#  cl100k_base: ~35 tokens —— GPT-3.5/4 词表，常用中文已是 1 token
#   o200k_base: ~33 tokens —— GPT-4o，进一步优化
```
